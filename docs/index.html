DeepSeek Harness 第三方插件 · MIT

时间窗限定的任务队列

白天把任务攒成卡片，等到设定的时间窗（例如 18:00–07:00）打开， 队列自动逐条领取任务、交给会话执行，夜里无人值守地干活。

它在 DSH 内置的「对话 / 轨迹」旁边加了第三个页面「任务」。关掉编辑器去睡觉， 早上回来，昨晚排的活已经跑完了。

Features

它解决什么问题

白天想到什么就丢进队列，晚上让它自己跑。下面是这个插件真正做的事情。

🕗 时间窗驱动

只有在配置的时间窗内，队列才会领取任务。窗口之外，卡片安静地排队，谁也不动。

🗂️ 按工作区隔离

在工作区里建的任务属于该工作区、只在该工作区执行，别的工区看不到。连执行用的会话也是按工作区独立的——一个工作区的任务绝不会被送进另一个工作区的会话。

1️⃣ 同时只跑一个

每个工作区同一时刻只跑一个任务。这是设计如此，不是设置项——避免同一个仓库被两个会话改乱。

⏱️ 按工作区设间隔

cooldownMinutes 按工作区设置，0 表示上一个结束后立即开始下一个；批次里第一个任务永不等待。

🌙 跨午夜与全天

18:00→07:00 表示跨午夜，18:00→18:00 表示全天。多个窗口任一打开即运行。

🌍 显式时区

时间按显式 IANA 时区解析（如 Asia/Shanghai），笔记本换时区不会悄悄改变窗口。

🙋 无人值守授权

autoApprove 打开时，队列驱动的会话不会停下来等人回答授权提示——否则深夜的任务会卡死。

📦 归档与清理

队列 / 归档 / 设置三个面板。「归档已完成 (N)」一键归档，「清空归档」点两次确认。

⚡ 立即执行

等不及窗口？卡片上的 ▶ 执行会立刻跑这个任务，忽略时间窗与执行间隔。

Windows

时间窗怎么读

一个工作区可以有多个窗口，任一窗口打开即可运行。每个窗口都是某个显式 IANA 时区里的本地时间区间。

18:00 → 07:00
跨午夜：傍晚开始，次日早上结束。典型的「睡前一挂」窗口。
18:00 → 18:00
表示全天：起点等于终点，整天都在窗口内。
12:00 → 13:00
普通同日窗口：起点小于终点，就是当天的这一段。
窗口为空
不排期：没有任何窗口打开，队列不领任务（手动 ▶ 执行仍然有效）。
🌍

时区是显式的，不会跟着笔记本漂移

窗口按 timeZone 指定的 IANA 时区解析，默认 Asia/Shanghai。你出差换了系统时区，窗口仍然按你写的墙上时间生效，不会悄悄移位或消失。

Quick start

快速开始

克隆仓库后在插件目录执行下面两步。需要 Node >= 18。

  1. 构建客户端 bundle

    把 src/ 下编号的源码拼接成一个浏览器侧单文件 client.js。

  2. 安装进 profile

    把插件链接进 DSH profile，并写入一行 patch。

  3. 打开「任务」页

    运行中的 dsh 会监听 cordis.patch.yml 并热加载插件，侧边栏「对话 / 轨迹」旁边就会出现第三个页面「任务」；如果没出现，刷新页面即可。

sh 
# 从 src/ 生成 client.js
node build.mjs

# 链接进 profile + 写入一行 patch
node install.mjs
sh 
# 查看当前安装状态
node install.mjs status

# 卸载
node install.mjs uninstall
sh 
# 构建并跑全部 189 个测试
node build.mjs && node --test test/
🔁

改动生效规则

  • 改了 host/：重启 DSH 才生效。
  • 改了 src/：先 node build.mjs 重新生成 client.js，然后刷新页面。

Configuration

配置项与默认值

下表是开箱即用的默认值。大多数配置是全局的，只有一个字段按工作区保存。

dsh-plugin-task-queue 配置默认值
配置项 默认值 作用域 说明
enabled true 全局 总开关。关掉后任何时间都不会领取任务。
windows [{ start: '18:00', end: '07:00' }] 全局 允许执行的时间窗列表，任一打开即可运行。空列表 = 不排期。
timeZone 'Asia/Shanghai' 全局 解析窗口所用的显式 IANA 时区。
autoApprove true 全局 跳过队列驱动会话的授权确认。见下方安全提示。
targetMode 'shared' 全局 任务会话的选择方式：shared（同一工作区内复用一个 runner 会话）或 fresh（每个任务新会话）。两种模式下会话都按工作区隔离。
taskTimeoutMinutes 360 全局 单个任务最长运行分钟数，超时标记为失败。
compactBeforeTask false 全局 共用会话时，在每个任务前先压缩上下文，代价是一次模型调用并丢失细节，因此默认关闭。
file '' 全局 队列文件路径。空 = <DSH_HOME>/task-queue/queue.json。
cooldownMinutes 0 按工作区 上一个任务结束后等待多久再开始下一个。0 = 立即开始；批次里第一个任务永不等待。

Unattended access

无人值守权限与它的风险

夜里的任务没有人在旁边点「允许」。插件的做法是主动把队列驱动的会话变成不需要授权的会话。

⚠️

安全风险：被队列驱动的会话拥有完全文件系统与命令执行权限

autoApprove 默认是打开的。打开时，经队列驱动的会话可以在不向你确认的情况下读写文件、执行命令。请只把任务排给你信任的内容，并在不需要无人值守时把它关掉。

三层绕过是怎么实现的

这三层都只对插件驱动的会话生效。你正在打字的会话（包括跑着这段对话的那个）不受影响。

  1. 设置会话的 sandbox/mode 为 danger-full-access——让文件系统与 shell 工具一开始就不需要提权。这一层决定活到底能不能干成。

  2. 在 tools/pre-execute 上注册监听器，对被托管的会话直接回答 allow。这是真正的绕过：它在 ask 变成审批请求之前就短路了工具流水线，且与会话携带的审批策略无关。

  3. 在 approval/request 上注册监听器，对被托管的会话回答 allowed-once，用来兜住那些直接向审批服务提问、而不是走 pre-execute 决策的工具。

🔒 作用域被限制住了

每一层都会先检查会话是否被本插件托管。没有排任何排队或运行中任务的会话、以及你手动开的会话，都不会获得这些授权。

🧯 想更保守？

把 autoApprove 关掉即可。代价是深夜的任务可能因为无人回答授权提示而失败——这正是默认打开它的原因。

Limitations

已知限制

这些是当前版本真实存在的边界，排任务前请先看一眼。

🔌 需要 DSH Host 在运行

队列由 Host 侧的插件驱动。Host 没起来，队列就不会动。

🔍 完成状态由 agent 状态推断

插件不是通过任务的「业务结果」判断成败，而是根据 agent 的状态推断，所以极少数情况下判定可能与你的直觉不同。

⏲️ 窗口精确到分钟

时间窗的最小粒度是分钟（HH:mm），没有秒级排期。

💥 崩溃可能让任务重跑一次

如果进程在任务执行中崩溃，重启后该任务可能被再跑一遍。因此任务指令建议写成幂等的——重复执行一次不会造成破坏。

🚧 任务不能跨工作区移动

任务属于创建它的工作区，不支持把它挪到另一个工作区去执行。

1️⃣ 每个工作区只跑一个

同一时刻一个工作区最多一个任务在跑。想并行就拆成多个工作区，而不是调大这个数——它不可配置。

FAQ

常见问题

关于时间窗、隔离、授权的几个高频疑问。

任务会在白天跑吗？

默认不会。默认窗口是 18:00–07:00，窗口之外队列不领取任务，卡片只是安静地排队。

如果你确实想立刻开工，卡片上的 ▶ 执行 会立即执行该任务，忽略时间窗与执行间隔。

我在 A 工作区建的任务，会在 B 工作区跑吗？

不会。任务按工作区隔离：在工作区里建的任务属于该工作区、只在该工作区执行，别的工区看不到。

而且任务不能跨工作区移动——想换地方执行，就在那个工作区里新建一条。

为什么每个工作区同时只跑一个任务？这是设置项吗？

是设计如此，不是设置项，也不能调。同一个工作区里并发改动代码，很容易让两个会话互相踩到对方的改动，所以串行是刻意的选择。

执行间隔（cooldownMinutes）在哪里设？

按工作区设置，不是全局的。它的含义是「上一个任务结束后等待多久再开始下一个」：

  • 0（默认）＝ 上一个结束就立刻开始下一个。
  • 批次里的第一个任务永不等待——间隔只发生在任务之间。
18:00 → 07:00 会被当成空窗口吗？

不会。起点大于终点表示跨午夜：从傍晚开始，到次日早上结束。这正是「晚上挂机干活」要的语义。

而 18:00 → 18:00（起点等于终点）表示全天。窗口列表为空才表示不排期。

我把笔记本带到别的时区，窗口会跟着变吗？

不会。窗口按 timeZone 里显式写明的 IANA 时区解析（默认 Asia/Shanghai），不依赖机器当前的系统时区。换时区不会悄悄改变窗口。

autoApprove 会不会影响我正在打字的会话？

不会。三层绕过都对插件驱动的会话生效，并且每一层都会先检查该会话是否被队列托管。你手动开的会话、以及你正在打字的会话都不会获得额外授权。

但它确实会作用于被队列驱动的会话——那些会话拥有完全文件系统与命令执行权限，请见页面上的安全提示。

改了代码要怎样让它生效？
  • 改了 host/：需要重启 DSH。
  • 改了 src/：先 node build.mjs，再刷新页面。
任务卡住了会怎样？

单个任务受 taskTimeoutMinutes 限制（默认 360 分钟 = 6 小时），超时会被标记为失败，队列可以继续往下走。

如果进程在任务执行中崩溃，重启后该任务可能被重跑一次，所以任务指令建议写成幂等的。

怎么卸载？

在插件目录执行 node install.mjs uninstall。想先确认当前状态用 node install.mjs status。
